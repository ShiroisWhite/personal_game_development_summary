# SOC 配置设计

## 原则

配置只承载三类东西：

1. **内容**：条目、文本、资源、关卡、掉落
2. **数值**：可调参数、概率、成本、产出
3. **开关**：功能开关、区域规则、条件

不符合这三类的，不要做成配置。**能由代码规则推导的，不要新增字段**。

## 流程

### 第 1 步：定义运行时状态

先写清楚：

- 这个系统有哪些状态？（未解锁 / 可建造 / 建造中 / 运行中 / 损坏 / 升级）
- 状态之间怎么迁移？触发条件是什么？
- 哪些状态需要持久化？

配置是状态的投影；状态没定义清楚，表一定设计错。

### 第 2 步：列实体与关系

```markdown
| 实体 | 主键 | 关键属性 | 关系 |
| --- | --- | --- | --- |
| Building | buildingId | 名称、等级、占地 | 1:N BuildingLevel |
| Recipe | recipeId | 输入、输出、时长 | N:1 Building |
```

关系要标出一对一、一对多、多对多，以及删除时的级联规则。

### 第 3 步：设计表结构

每张表给出：

```markdown
### 表名：Building

| 字段 | 类型 | 必填 | 默认值 | 说明 | 引用 |
| --- | --- | --- | --- | --- | --- |
| buildingId | int | 是 | - | 主键，连续不跳号 | - |
| nameKey | string | 是 | - | 多语言 Key | Lang.xlsx!key |
| maxLevel | int | 是 | 1 | 最大等级 | - |
```

字段规则：

- 主键稳定、可读、不随内容改号
- 外键必须写明引用表与字段
- 枚举值写全，不留“其他”
- 默认值明确，避免空值歧义
- 概率/权重写清楚分母
- 时间单位统一（秒 / 毫秒），在表头注明

### 第 4 步：检查引用链

逐条检查：

- 每个外键都有目标行
- 每个被引用行都有消费方
- 删除某行时，引用方是否会悬空
- 多语言 Key 是否都存在
- 客户端/服务端导出路径是否一致

### 第 5 步：验收用例

至少写 5 条：

1. 正常路径
2. 边界值（最小/最大/空）
3. 非法值（越界、缺引用）
4. 状态迁移异常
5. 删除/回滚

每条写：输入 → 期望结果 → 实际检查方式。

### 第 6 步：变更影响

- 影响哪些系统、哪些表、哪些导出
- 是否需要兼容旧存档/旧数据
- 是否需要灰度或开关
- 回滚方案

## 读取现有 Excel

使用工具，不要用肉眼猜：

```bash
python tools/excel_inspect.py sheets  "路径/配置.xlsx"
python tools/excel_inspect.py schema  "路径/配置.xlsx" --sheet Sheet1
python tools/excel_inspect.py sample  "路径/配置.xlsx" --sheet Sheet1 --rows 10
python tools/excel_inspect.py search  "路径/配置.xlsx" --keyword 建造
```

工具会输出表头、样例行和类型推断。表头通常在前几行，注意区分：

- 第 1 行：字段名
- 第 2 行：中文说明 / 类型
- 第 3 行起：数据

不同项目行号不同，以底座中的说明为准；底座没写就明确问用户。

## 输出结构

```markdown
## 结论
（需要新增/修改哪些表，一句话）

## 状态机
（状态与迁移）

## 实体关系
（表 + 关系）

## 表结构
（逐表字段）

## 引用链检查
（悬空 / 缺失 / 冗余）

## 验收用例
（5 条以上）

## 变更影响与回滚
```

## 质量门槛

- 不新增无消费方的字段。
- 不把代码逻辑塞进配置。
- 不编造表名、字段名、Sheet 名。
- 用户是策划：需要改代码时，指出文件与行号，不要让他自己调试。
- 涉密配置只在本地读取，不上传外部服务。
