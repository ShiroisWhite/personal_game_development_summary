# 沙盒生存策划助手

> 这不是一篇介绍文章，是这套助手的**实际配置**：目录结构、常驻指令、技能清单、知识底座、记忆规则、以及换一个项目时怎么挂上去。
> 涉及具体项目的内容已脱敏——路径、表名、工程位置以占位符代替，结构与规则保持原样。

---

## 一、它是什么

一句话：**面向 SOC（生存建造开放世界）策划的设计顾问 + 工作台。**

它的默认输出不是"帮你写"，而是先把问题拆清楚：结论在前，事实、推断、假设、未知分开标注；能给出选项、代价与推荐，但不替你决定"哪个更好玩"。

三类任务最常见：

| 你在做什么 | 它给什么 |
| --- | --- |
| 判断一个设计成不成 | 定位三问 → 循环图 → 结构/数值判定 → 失败模式 → 最小验证 |
| 把想法落成配置 | 实体关系 → 表结构 → 字段与引用链 → 验收用例 |
| 换到新项目 | 一条命令挂载目录，自动建底座、扫配置表、同步路径 |

---

## 二、四层结构

和大多数"提示词角色"不同，这套东西是**四层叠起来的**，每层解决一个不同的问题：

```
SOC-Assistant/
├── AGENTS.md              ← 宪法：身份、启动流程、信息分层、工作原则、边界
├── ONBOARDING.md          ← 上手：三条命令、能力表、新项目接入、FAQ
├── skills/                ← 工具：20 个技能，每个一个 SKILL.md
├── bases/soc-general/     ← 内容：26 篇方法论 + 4 个模板（通用层）
│   ├── knowledge/         ←   01-05 核心框架 + 「主题-体裁」题材手册
│   ├── templates/         ←   系统说明 / 配置规划 / 评审 / 循环图
│   └── INDEX.md
├── memory/                ← 经验：索引 + 每条一个文件的长期记忆
└── tools/                 ← 8 个 Python 工具：挂载、检索、索引、校验、导出
```

四层分工：`AGENTS.md` 是**宪法**（每次必读）→ `skills/` 是**工具**（按需触发）→ `bases/` 是**内容**（问到才查）→ `memory/` 是**经验**（相关才召回）。

关键设计是**内容与项目分离**：方法论永远通用，具体游戏的数值、表名、路径全部放在"项目底座"里，不写进核心文件。所以换项目不需要改核心，只需要挂一个目录。

---

## 三、技能池：21 个里挑 20 个

技能不是"知道得越多越好"，而是"**在该被用到的时候被用到**"。每个技能的 `description` 就是触发器。

| 类别 | 技能 | 什么时候用 |
| --- | --- | --- |
| 设计判断 | `sandbox-survival-consultant` | 以顾问视角讨论一个系统该怎么做 |
| 拆解 | `soc-system-teardown` | 拆一个具体系统（家园、建造、载具……） |
| 循环 | `soc-loop-diagnosis` | 核心循环哪里断了、经济为什么不成立 |
| 对标 | `soc-competitor-analysis` | 拆竞品、提炼可迁移结论 |
| 压力测试 | `design-grill` / `grilling` | 连续追问，暴露最弱假设 |
| 配置 | `soc-config-design` / `config-finder` / `config-planner` | 需求 → 配置结构；或反查一个配置在哪 |
| 文档 | `soc-design-doc` | 策划案、需求文档、系统说明 |
| 原型 | `soc-prototype` / `game-ui-prototype` | 单文件 HTML 高保真原型 + 截图 |
| 术语 | `domain-modeling` | 统一叫法、记录设计决策 |
| 底座 | `content-base-router` | 查看/切换/新增内容底座 |
| 记忆 | `memory-curator` | 写入、更新、召回长期记忆 |
| 工程 | `xlsx` / `unity-developer` / `find-skills` | 表格、Unity、找技能 |

技能来自不同地方（自己写的、迁移包里的、同事的），但**使用与导出一视同仁**——这是一个共享池，不按作者分层。

### 一个技能长什么样

以 `soc-config-design` 为例：

```
---
name: soc-config-design
description: 从策划案推导配置表结构、字段、引用与验收……（决定何时触发）
---

# 配置设计

## 第一步：先判断这是不是配置问题
    ⚠️ 不需要配置的情况        ← 显式排除项，治过度设计
## 第二步：实体与关系
## 第三步：表结构与字段
## 第四步：引用链与校验
## 第五步：验收用例
## 输出格式（固定五段）
```

三个可复用的点：**description 决定触发**、**显式写排除项**、**固定输出格式**。

## 四、知识底座：26 篇

通用底座 `soc-general` 里有 26 个文件，命名即分类：

| 前缀 | 内容 |
| --- | --- |
| `01-` | SOC 核心方法论（五链、局容器、时间层与身份层） |
| `02-` | 循环模式库（哪些循环结构成立、哪些是管子） |
| `03-` | 结构诊断法（定位三问、三轴判定） |
| `04-` | 失败模式库（四死法：管子非循环 / 僵尸系统 / 操作粒度泄漏 / 误建模） |
| `05-` | 设计评审清单 |
| `主题-体裁` | 家园、载具、生存属性、采集链路、射击战斗、交互易用性、宠物繁育、轮盘、种植养殖…… |

总红线一句话：**放大器必配消耗链与风险阀门。**

## 五、即插即用：换一个项目只要一条命令

```
python tools/mount_project.py "D:\资料\某游戏" --id my-game --name "某游戏"
```

这一条命令做五件事：

1. 在目录下建 `base.json` + `INDEX.md`（自动扫描 md / txt / **xlsx 配置表**）
2. 建 `knowledge/`、`templates/`、`cases/` 三个空目录
3. 注册进 `bases/registry.json` 并激活
4. 若目录里有 `paths.json`，**同步九类项目路径**到技能
5. 之后 `kb_search.py` 可以全文检索，Excel 也能搜到具体单元格

路径只在一个地方配：`skills/_project-paths.json`（九类字段：引擎、工程根、C#/Lua、预制体、配置表、语言表、原型输出、记忆根）。字段留 `null` 表示没有该资源，技能会跳过对应链路，而不是猜路径。

## 六、一份内容，三种运行时

同一份内容可以导出成三种形态：

| 目标 | 产物 |
| --- | --- |
| dsh（本机） | 直接运行，技能以目录链接安装 |
| Claude Code | `CLAUDE.md` + `.claude/skills/` |
| Codex | `AGENTS.md` + `.agents/skills/` |

导出时自动做两件事：**跳过 confidential 项目底座**、**把项目路径清空**（`_project-paths.json` 字段全 null）。

---

## 七、边界

这套配置**不绑定任何具体项目**，但也因此有三条明确的边界：

1. **导出物不含 `tools/`** —— 在 Claude Code / Codex 里能用技能和方法论，但挂项目、扫配置表要回源包执行。
2. **不含项目底座** —— 通用层只有方法论；具体游戏的资料要靠 `mount_project.py` 挂进来，且默认标 confidential、不导出。
3. **不含企业协作类集成** —— 飞书文档、企业内部表这类依赖账号权限的东西刻意留在外面。
