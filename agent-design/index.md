# 领域智能助手：把项目知识变成可检索的资产

> 本文不是"如何用 AI 提效"的经验帖。它回答一个更窄的问题：
> **当一个策划每天大半时间都在"查依据"，怎么把这件事做一次、反复用。**

---

## 一、问题的形状

策划的日常不是"想设计"，是"查依据"。

一个需求要落地，至少要回答四个问题：

1. **需求文档怎么写的？**（在线协作文档）
2. **配置表里有没有对应字段？**（Excel / 配置表）
3. **代码在哪一层读它？**（工程代码）
4. **界面上它挂在哪？**（预制体组件参数）

这四个答案分散在**四个互不相通的系统**里。默认解法是人工在四者之间来回搬信息——而搬的过程本身会产生新问题：**文档描述与配置实现经常不一致。**

所以真正的成本不是"查得慢"，而是：

> **查完之后，你并不确定自己查到的是不是真的。**

问题因此可以重新定义为：**不是让查得更快，是让查到的答案可信、可追溯、可复用。**

---

## 二、三层做法

### 第 1 层 · 接入：把数据源放进同一个上下文

把四类（实际是五处）数据源接进同一个可检索的上下文：

| 数据源 | 作用 |
| --- | --- |
| 在线需求文档 | 需求"应该是"什么样 |
| 数据配置表 | 数值与规则"实际"怎么配 |
| 多语言表 | 玩家看到的文案从哪来 |
| 工程代码 | 哪一层在读这份配置 |
| **预制体组件参数** | **配置不一定在表里——很多参数直接序列化在预制体上** |

最后一条是多数人忽略的：**搜完表搜不到，不等于没有配置，很可能是挂在组件上了。** 这条规则写进助手的常驻约束之后，"找不到"的情况明显减少。

### 第 2 层 · 封装：把反复出现的任务做成可复用的技能

判断标准很简单：**一个动作如果一个月内重复 3 次以上，且每次都要重新想"从哪开始"，就值得封装。**

实际封装的几类：

- **配置查找**：给定一个功能名，自动在五处数据源里交叉定位，并给出"文档说的 / 配置有的 / 代码读的"三方对照
- **需求拆解**：给一份策划案，输出"要改哪些配置表、哪些字段、哪些代码改动点"
- **活动配置设计**：按既有的数据结构生成配置骨架并自检
- **资料库导航**：在大量策划文档里定位到相关的那几篇

关键在于：**技能封装的不是"知识"，是"路径"。** 它回答的是"这类问题该按什么顺序查"，而不是"答案是什么"。

### 第 3 层 · 沉淀：把每次排查的结论写回去

规则只有两条：

1. **只写"以后还会用到"的结论**——某个参数在哪张表、某个现象的根本原因
2. **不写过程、不写猜测**——过程是这一次的，猜测会污染下一次

积累到一定量之后，效果会发生质变：**新问题的起点不再是零，而是过去所有排查的终点。**

---

## 三、三个关键取舍

### 取舍 1 · 先做"能查"，再做"能判"

同一个助手可以做两件事：

- **查**：确定性的——参数在哪、谁在读它。答案对错可验证
- **判**：模糊的——这个设计好不好、该怎么改。答案取决于判断框架

**顺序很重要。** 查是地基：没有可信的事实，判断就是空谈。所以先做查，把确定性做扎实；再往上叠判断。

### 取舍 2 · 可迁移内核与项目事实必须分离

这是整套设计里最重要的一条。同一个助手里，两类知识的**生命周期完全不同**：

| | 项目事实 | 方法论 |
| --- | --- | --- |
| 例子 | 某参数在哪张表、某段代码在哪一层 | 「产能 = 风险阀门 + 零和掠夺 + 正和养成回收」 |
| 换项目 | **作废** | **照常可用** |
| 载体 | 绑定具体工程 | 可独立成篇 |

所以要把它们做成**两个独立的层、两个不同的角色**：

- **事实层**：绑定工程，负责"查"
- **方法层**：剥离项目数值，只留可迁移的判断框架，负责"判"

这也是为什么那份方法论里几乎看不到任何具体项目的名字和数字——**它是被刻意"去项目化"的**。项目事实只作为浅案例出现，且明确标注"不是设计标准"。

### 取舍 3 · 知识要写回，不能留在对话里

一次排查如果只在当次对话里得出结论，下次等于没做过。

所以设计上强制了一件事：**有价值的发现必须落盘成结构化条目**，而不是留在聊天记录里。否则这个助手的价值会随对话结束而清零。

---

## 四、效果

| 维度 | 之前 | 之后 |
| --- | --- | --- |
| 写需求前 | 先问程序"这个能不能做" | 自己先查清落地方案与实现成本 |
| 跨职能对接 | 拿着示意图反复口头确认 | 结论一次对齐，基本一遍过 |
| 新人接手 | 从零摸清系统 | 有可检索的知识底座 |

---

## 五、边界：这套东西不能直接搬走

**这套助手是深度绑定具体工程的。** 换一个项目，接入层要重搭、知识库要重积累。

但它证明的能力是可迁移的：

> **知道该把哪些项目知识编码进去，知道怎么把"路径"和"答案"分开封装，知道怎么让事实层与方法层互不污染。**

这三件事与具体项目无关——**换一个工程，用同样的方法再做一遍即可。**
