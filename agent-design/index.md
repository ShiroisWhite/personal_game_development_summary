# Claude Code 领域智能助手

> 这不是一篇介绍文章，是这套智能体的**实际配置**：目录结构、常驻指令、技能清单、记忆规则。
> 涉及具体项目的内容已脱敏——路径、表名、代码位置以占位符代替，结构与规则保持原样。

---

## 一、目录结构

智能体由四层组成，全部是纯文本，跟着仓库走：

```
~/.claude/
├── CLAUDE.md                  ← 常驻指令：身份、资源地图、工作方式、路由、边界
├── skills/                    ← 12 个技能，每个是一个 SKILL.md
│   ├── config-finder/         ←   跨五处数据源定位一个配置
│   ├── config-planner/        ←   策划案 → 配置与代码改动清单
│   ├── excel-config-analyzer/ ←   表结构、字段语义、跨表引用
│   ├── activity-designer/     ←   多周线性任务活动的配置设计
│   ├── project-manager/       ←   项目管理与协作文档集成
│   ├── library-navigator/     ←   文档库导航
│   └── domain-modeling/       ←   领域术语与架构决策记录
├── projects/<project>/
│   └── memory/                ← 97 条结构化记忆 + 一份索引
│       ├── MEMORY.md          ←   一行一条的索引（每次会话自动加载）
│       └── *.md               ←   每条记忆 = 一个事实 + Why + How to apply
└── settings.json              ← 模型、环境变量等运行配置
```

**四层的分工**：`CLAUDE.md` 是宪法（每次必读）→ `skills/` 是工具（按需触发）→ `memory/` 是经验（相关时召回）→ `settings.json` 是运行环境。

---

## 二、CLAUDE.md：常驻指令的四个部分

它的作用是**把"这个项目该怎么工作"写死**，避免每次会话重新解释。真实结构如下（内容脱敏）：

### 1 · 项目身份

一句话锁定"不认识的词指同一件事"，防止模型把同一个项目当成几个不同工程重复建档。

### 2 · 资源地图

| 资源 | 位置 | 说明 |
| --- | --- | --- |
| 记忆 | `~/.claude/projects/<project>/memory/` | 90+ 条取证与方法论 |
| 方法论大脑 | `<本地知识库目录>` | 智能体总纲、知识与技能索引 |
| 策划资料库 | `<对外只读的大体量文档库>` | 按大类索引，只读引用 |
| 技能 | `~/.claude/skills/` | 12 个 |

关键是**原位引用、不整体复制**——大体量资料不搬进工作区，只维护索引。

### 3 · 工作方式

- **结论 / 状态在前**，依据与行动项在后
- **信息分层**：任何结论必须区分「已确认事实 / 用户反馈 / 推断 / 待验证假设 / 未知」，不把推断升级为事实
- **主动提问**：会改变方向、范围、优先级、成本的不确定性必须问；可逆的低风险缺口标假设继续
- **阶段复盘**：完成与证据、遗留问题、可改进思路、最小可验证的下一步
- **需求收敛**：先冻结需求合同（使用者 / 用途 / 载体 / 篇幅 / 验收 / 排除项），再分层交付
- **角色边界**：使用者是策划，只能查改配置表。代码侧根因必须指到文件行号，交程序处理——不让模型假装能调试

### 4 · 查什么 → 走哪里

一张路由表，把「我想问什么」映射到「该读哪里 / 哪个技能」。这是最省事的一节：有了它，每次提问都不用再描述背景。

### 5 · 边界

哪些目录只读、密钥不落盘、历史约束不覆盖用户的新决定。

## 三、技能：把反复出现的任务封成可调用单元

判断标准：**一个动作一个月内重复 3 次以上，且每次都要重新想"从哪开始"，就值得封装。**

当前安装 12 个，其中与项目强相关的是这 7 个：

| 技能 | 行数 | 作用 |
| --- | --- | --- |
| `config-finder` | 182 | 在需求文档 / 配置表 / 多语言表 / 代码 / 预制体五处交叉定位一个配置 |
| `config-planner` | 120 | 输入一份策划案，输出「要改哪些表、哪些字段、哪些代码点」 |
| `excel-config-analyzer` | 66 | 表结构、字段语义、跨表引用、导出路径 |
| `design-linear-task-activity` | 54 | 多周线性任务活动的配置设计与校验 |
| `manage-game-development` | 101 | 项目管理：排期、依赖、风险、复盘 |
| `planning-library-navigator` | 48 | 大体量文档库的定位与检索 |
| `domain-modeling` | 74 | 领域术语表与架构决策记录 |

### 一个技能长什么样

以 `config-planner`（120 行）为例，它的真实骨架：

```
---
name: config-planner
description: 根据策划案分析需要新增或调整的配置表与代码改动点。
             （这一句决定什么时候被触发）
---

# 配置规划助手

## 项目路径速查          ← 让技能知道去哪找
## 工作流程
   第一步：输入理解      ← 先判断这是不是一个「需要配置」的需求
   ⚠️ 不需要配置的情况    ← 显式排除项，防止过度设计
   第二步：参考已有系统
   第三步：输出配置规划
## 输出格式
   一、新增 / 修改配置表（新建表 / 新增字段 / 新增数据行，分三类）
   二、新增多语言表条目
   三、代码改动建议
   四、无需配置的部分 ⚠️
   五、风险 & 注意事项
## 关键规则
```

三个可复用的点：

1. **description 决定触发**——技能不是"知道得越多越好"，而是"在该被用到的时候被用到"
2. **显式写排除项**（"不需要配置的情况"）——反向约束比正向描述更能治过度设计
3. **固定输出格式**——让产出可以直接被程序或人接手，而不是每次换一种说法

## 四、记忆：把结论写回去

当前 **97 条**，每条一个文件，格式固定：

```
---
name: <短横线slug>
description: <一行摘要，用于判断相关性>
metadata:
  type: project | user | feedback | reference
---

<事实本身>

**Why:** 为什么会记这条
**How to apply:** 什么情况下该用
```

配套一份 `MEMORY.md` 索引，一行一条，**每次会话自动加载**——先看索引，按需再展开具体条目。

**三条写入规则**：

| 规则 | 原因 |
| --- | --- |
| 只写"以后还会用到"的结论 | 过程是这一次的，结论才是资产 |
| 不写猜测 | 猜测会污染下一次的判断 |
| 必须写 Why 与 How to apply | 没有上下文的结论，下次会被误用 |

---

## 五、这套配置解决的是什么

| 问题 | 配置怎么解 |
| --- | --- |
| 每次会话都要重新交代背景 | `CLAUDE.md` 把身份、地图、路由、边界写死 |
| 同一类任务每次从头想 | `skills/` 把"路径"封装，而不是把"答案"封装 |
| 查过的东西下次还要再查 | `memory/` 把结论写回，新问题的起点是上次的终点 |
| 模型把推断说成事实 | 工作方式里强制分层：已确认 / 推断 / 待验证 / 未知 |

---

## 六、边界

这套配置**深度绑定具体工程**——路径、表结构、术语都是那一套。换一个项目，四层都要重建。

但重建时**知道该写什么**：身份怎么写、地图怎么排、路由怎么分、技能按什么粒度切、记忆按什么规则收——这部分与具体项目无关。

配置形态本身是可以直接搬的：`CLAUDE.md` + `skills/` + `memory/` 全是纯文本，随仓库走。
