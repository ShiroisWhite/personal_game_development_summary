用户反复遇到"一个功能文档点太多、不够精"（曾把 31517 字符压到 15920，瘦身约 50%）。

**拆法：一主两子**

| 层 | 内容 | 是否可跨系统迁移 |
| --- | --- | --- |
| 设计层（主文档） | 系统怎么被设计得成立：大法则、通用原则、评审 checklist、补强方向 | 可迁移，**留主文档** |
| 落地层（子文档） | 这个系统具体怎么回事：实现流程、取证、优缺点、战斗拆解、架构图 | 不可迁移，只作证据 |
| 优化层（子文档） | 已成立系统怎么优化得顺手：交互易用性类可复用总纲 | 跨案复用 |

**要点**
- 主文档保留「现状诊断」摘要框作引子，不随拆解搬走，用来承接补强建议。
- 架构图 / 画板放子文档，主文档 0 画板。
- 子文档挂在主节点下，主文档开头放跳转链接。
- 拆完自检：链接指向两子、诊断框在补强建议前、画板数=0。

**How to apply:** 下次再遇到臃肿功能文档，先问"里面混了几层？每层受众和复用价值是否不同？"混了才拆，不混别硬拆。
