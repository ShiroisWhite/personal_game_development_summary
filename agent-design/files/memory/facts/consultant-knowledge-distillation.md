用户要做的不是"能查工程/查 Excel 的助手"，而是**能跨游戏通用的设计头脑**。蒸鹰基调（2026-09 与用户拍板）：

**纯方法论内核 + 浅案例点缀**
- 把"XX 表第几行 / XX 数值 / XX.file:line"这类**项目事实去项目化**，抽象成可迁移的设计原则/框架/判据。例：集水器水量 3000/4500/7500 → "容量随等级阶梯化，增幅由成长曲线定"。
- 项目事实**只当参考**（齐谐、举例），**不当设计标准**。可保留"可迁移设计陷阱原型"（发电误建模/马匹替代/逐级作物），讲成**模式**而非"本作就是这样"。
- 用户明确决策：纯方法论 + 浅案例。不做"拆解 + 方法论"混合版（取证太厚、太费页）。
- 手册标题不带项目名，用"这类系统"而非"本作"。

**格式纪律**
- 产物必须是 **`.md` 纯文本**；**PDF 不能当知识库**（读 PDF 依赖 poppler/pdftoppm 图像渲染，新环境缺失就读不出）。迁移的顾问知识必须纯文本。

**何时用：** 铺开任何系统（玩法循环、生存属性、采集、载具、射击）的方法论时，用同一套"纯方法论 + 浅案例"蒸馏；先答灵魂问题再定位。
