# 策划案 / 需求文档

## 文档分层（先判断再动笔）

一份文档如果同时装着方法论、具体证据和优化建议，就会臃肿。先分层：

| 层 | 内容 | 是否跨项目复用 |
| --- | --- | --- |
| 设计层（主文档） | 系统怎么成立、规则、评审标准、补强方向 | 可复用 |
| 落地层（子文档 A） | 本项目的实现、取证、配置、优缺点 | 不复用 |
| 优化层（子文档 B） | 已成立系统的交互/易用性优化方法 | 可复用 |

只写一层；混层时先拆。

## 标准章节

```markdown
# 【设备/范围】功能名称

## 1. 更新日志
| 时间 | 修改内容 | 修改人 |

## 2. 设计目的
为什么要做；不做会怎样；服务哪条循环/哪类玩家。

## 3. 系统概述
一句话定义 + 功能全貌。

## 4. 范围与非目标
做什么；明确不做什么（防止评审跑偏）。

## 5. 规则与状态机
状态列表、迁移条件、持久化、异常状态。

## 6. 交互与流程
玩家操作路径；关键界面；异常与空态。

## 7. 配置
需要新增/修改的表、Sheet、字段、引用；见配置清单。

## 8. 数值
关键参数、公式、上下限、成长曲线；标注“设计建议”或“现有配置”。

## 9. 多语言与文案
新增文本、Key、格式占位符。

## 10. 验收标准
可观察、可复现的通过条件。

## 11. 风险与依赖
技术风险、内容风险、排期依赖、回滚方案。

## 12. 后续规划
未决问题、未来方向、明确延期项。
```

## 写作规则

1. **先结论后细节**：每节开头一句话说清这一节要解决什么。
2. **规则写成判定式**：`当 A 且 B 时，执行 C；否则 D`。避免“尽量”“适当”。
3. **状态必须有名字**：不要用“正常/异常”这种模糊词。
4. **数值标来源**：现有配置 / 设计建议 / 待定，三选一。
5. **配置与规则分离**：规则说“怎么算”，配置说“用哪些数”。
6. **验收可复现**：写清前置条件、操作、期望结果。
7. **非目标要写**：明确排除项，比补充说明更能减少返工。

## 重构臃肿文档

1. 标出文档里混了几层（设计/落地/优化）。
2. 主文档只留可迁移的设计规律与评审标准。
3. 具体证据、截图、配置、实现细节移到落地层子文档。
4. 交互/易用性方法移到优化层子文档。
5. 主文档开头放子文档跳转，保留一段紧凑的“现状诊断”作为引子。
6. 拆完检查：链接可达、诊断在补强建议之前、没有遗留的重复段落。

## 输出结构

先给目录，再给正文。正文按章节写，不跳节；信息不足的章节写“待补：需要什么信息”，不要用套话填充。

## 质量门槛

- 不写无法验收的形容词。
- 不把设计建议写成现有配置。
- 不遗漏非目标、异常状态、回滚方案。
- 涉密项目的文档只在本地生成，不发送外部服务。
- 用户是策划：涉及代码改动时给出文件与行号，供转交程序。
