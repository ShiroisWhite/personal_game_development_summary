# SOC 竞品拆解

## 证据分级（必须标注）

| 级别 | 来源 | 可信度 |
| --- | --- | --- |
| A | 公开可验证：官方文档、版本说明、实机演示、开发者访谈 | 高 |
| B | 可复现观察：自己游玩、截图、录像、社区共识 | 中 |
| C | 推断：从设计逻辑反推，未验证 | 低 |
| D | 传闻/二手转述 | 不作为结论依据 |

输出中每条结论都要带级别。A/B 才能进入“可迁移结论”，C 只能作为假设。

## 对标维度

按以下维度建立矩阵：

| 维度 | 看什么 |
| --- | --- |
| 核心循环 | 生存压力 → 采集 → 建造 → 战斗 → 社交的闭环 |
| 生存压力 | 来源、强度、持续时间、后期是否消失 |
| 建造深度 | 自由度、模块化、结构规则、防御价值 |
| 制作/生产 | 工序链、中间产物、自动化程度 |
| 战斗 | 操作层、成本、PvP/PvE 比例、装备损耗 |
| 社交/对抗 | 组队、交易、掠夺、GVG、零和/正和 |
| 进度 | 等级/科技/图鉴、赛季/wipe、封档方式 |
| 经济 | 货币产出、回收、通胀控制 |
| 内容节奏 | 单局时长、更新周期、内容消耗速度 |
| 失败模式 | 僵尸系统、管子、操作粒度、强者恒强 |

## 流程

1. **定义对标目的**：你要验证哪个设计假设？没有目的的对标只会变成功能清单。
2. **选 2–4 个样本**：至少一个同品类标杆、一个相邻品类、一个反面样本。
3. **填矩阵**：只填有证据的格子；空格标“未知”，不要猜。
4. **找差异**：不列“它有什么”，只列“它在哪个结构上和我们不同”。
5. **判断可迁移性**：

| 结论 | 条件 |
| --- | --- |
| 可直接迁移 | 结构相同、玩家预期相同、成本可控 |
| 需改造 | 结构相同但节奏/成本不同 |
| 不可迁移 | 依赖不同的核心体验或商业模式 |
| 反面教材 | 它踩过的坑，我们有同样结构风险 |

6. **落到我们的约束**：团队规模、研发周期、目标用户、变现方式。脱离约束的“抄”没有意义。

## 输出结构

```markdown
## 结论
（最值得借鉴的 1–2 点，以及最不该抄的 1 点）

## 对标矩阵
| 维度 | 样本 A | 样本 B | 我们 | 差异 |
|---|---|---|---|---|

## 关键结构差异
（逐条：它怎么解，我们怎么解，为什么不同）

## 可迁移结论
（可直接用 / 需改造 / 不可用 / 反面教材）

## 证据与未知
（分级列出）

## 风险
（迁移后最可能出问题的地方）
```

## 质量门槛

- 不把功能清单当对标结论。
- 不把 C 级推断写成 A 级事实。
- 不忽略商业模式与团队约束。
- 引用竞品时注明版本与时间；版本差异会影响结论。
- 涉密底座中的项目信息不得出现在竞品报告的外部版本里。
