# 生存属性系统 · 方法论手册（沙盒生存通用）

> 适用：任何有"饱食 / 水分 / 热量 / 体重 / 三维"或其他会互相转化的生存属性的游戏。
> 纯方法论 + 浅案例。仅作设计原理参考，**不是任一游戏的标准**。

---

## 0. 一句话定位

生存数值不是"几条血条"，而是一套会**互相转化的状态机**，且**由服务器权威结算**。管好它，靠三层骨架 + 认准"配置载体"。

---

## 1. 三层骨架

- **属性定义层**：用一套**稳定命名的属性 ID 表**集中管理（饱食 / 水分 / 热量 / 肌肉 / 体重 / 三维…），不散落。
- **属性互转层**（核心）：属性之间互相转化的系数，落地到一张**稳定的"属性兑换表"**（源属性 → 目标属性 → 兑换系数）。**别把这些系数散成"随手借用的参数编号"。**
- **消耗规则层**：行为（移动 / 冲刺 / 采集 / 制作）消耗什么、多少。

> 三层里最容易出事的是互转层——它写成一张可维护的兑换表，整个系统才稳。

---

## 2. 服务器权威（多人必须）

**消耗 / 转化结算在服务器**；客户端只做：读推送值、行为"不足校验"、转化预览计算。防外挂、保结算一致。

---

## 3. 状态门槛（Buff）

饿 / 渴 / 吃饱喝足这类"状态"不只看数值，还应有**触发门槛的 Buff**（效果 + 显示开关）。数值是油箱，Buff 是走到临界后的"系统行为"。

---

## 4. ⚠️ 文档 vs 实现脱节（最值复盘的坑）

数值旋钮长期**散落在随手借用的参数 ID 上**，重构 / 换表 / 弃用后，文档与实现必然脱节——按文档编号调数值会"调了个寂寞"（编号早被弃用，真正活跃的系数在别处）。

**教训**：尽早让属性互转系数落地到一张稳定的"属性兑换表"，文档写清**配置载体**（哪张表、哪个字段），别只记编号。

---

## 5. 决策检查清单（上线前自检）

- [ ] 属性 ID 集中在稳定表了吗，还是散落？
- [ ] 互转系数有没有落到一张可维护的"兑换表"？还是随手借用参数编号？
- [ ] 消耗 / 转化在服务端结算吗（多人）？客户端只做预览？
- [ ] 状态类属性有触发门槛的 Buff 吗？
- [ ] 文档写的是"配置载体"还是"参数编号"？编号源还活吗？

---

## 6. 附：一条可复用红线

**互转系数进"兑换表"，文档写"载体"不写"编号"；消耗落服务端。** 三件都做到，系统十年不腐。

---

## 7. 附：可迁移的"设计陷阱"原型（浅案例）

- **按编号调值调到寂寞**：文档说"参数 738-743"管某系数，实际那些编号早标弃用，真系数在别表。→ 教训：**认准"配置载体"而非"编号"。**
- **属性段集中 vs 散落**：基础生存属性集中在连续段好管；散落则改一处牵全身。
