# SOC 系统设计方法论

> 一套"沙盒生存游戏的设计尺子"。
> 7 篇全部是**可迁移内核**——项目事实只在浅案例里作佐证，**不当标准**。

---

## 怎么用（顺序固定，先答再查）

1. **先答灵魂问题**：这套系统是给"想动脑的策略玩家"，还是"想省心的挂机玩家"？两端爽点相反，别混做。
2. **再做定位三问**：它改变玩家哪种状态 / 制造什么决策 / 产出去了哪成环了吗。
3. **用四死法诊断**：管子非循环 / 僵尸系统 / 操作粒度泄漏 / 误建模。
4. **按题材查对应手册** ↓

## 跨系统总红线

> **凡要"配置化"的 → 留表；凡要"改手感 / 节奏"的 → 用参数曲线；凡要"起冲突"的 → 给惩罚留抢救口；凡是"放大器 / 产能"的 → 必配一条"消耗链 + 风险阀门"。**

---

## 这些方法论是怎么来的

它们不是读书笔记，是**从一个真实项目的系统拆解里抽象出来的**：

- 先把具体系统拆到"哪个字段控制什么行为"的颗粒度
- 再把"这个项目怎么做"抽象成"这类系统的一般规律"
- 最后把项目事实剥离出去，只留下换一个游戏照样成立的部分

这套"去项目化"的过程本身，和 [领域智能助手](../agent-design/) 里讲的**「可迁移内核与项目事实分离」**是同一条原则。
